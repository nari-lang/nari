# Debugging Nari functions with GDB

Load the Nari GDB commands before starting the program:

```sh
gdb -q -x gdb/nari.py --args ./build/release/nari test.nari
```

At the GDB prompt:

```gdb
nari-break __top_level__@test.nari
run
nari-disassemble
nari-bytecode
```

`nari-break` stops before the first bytecode instruction of the named Nari
function or source module. It also works for embedded standard library modules:

```gdb
nari-break __top_level__@<std>/uuid
run
nari-disassemble
```

Named functions work the same way, for example `nari-break binary_neighbors`.
You can set more than one `nari-break` before `run` or while stopped at one.
`nari-disassemble` prints the function's source file; if the source is missing,
it prints bytecode. `nari-bytecode` always prints only that function's bytecode,
or the selected module's bytecode range inside `<main>`.

`nari-break` sets `NARI_GDB_FUNCTIONS=1` and `NARI_DISABLE_JIT=1` before the
inferior starts. The latter keeps every Nari call on the interpreter path so a
source-level breakpoint cannot be bypassed by a compiled call. To inspect
machine code generated by the JIT, start a separate GDB run without
`nari-break`, set a pending native breakpoint such as
`break nari_jit_binary_neighbors_ir_reg`, and use GDB's `disassemble` command.

The source-module names are parser names, not native ELF symbols. Their
statements are compiled into `<main>`, so plain GDB `break
__top_level__@test.nari` cannot resolve them. The Nari GDB commands use a
bytecode module marker and a native entry hook to stop at the correct point.
